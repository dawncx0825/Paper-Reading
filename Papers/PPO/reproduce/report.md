# Qwen 单卡复现方案：SFT → RM → PPO

> 创建日期：2026-09-20；正式运行完成：2026-09-21（新加坡时区）。第 1～11 节保留原始复现规划与预算，实际执行配置、实测结果、限制和结论见第 12 节。完整流水线在 RTX 3090 上以退出码 0 完成，最终测试已执行。

## 1. 目标与复现边界

复现论文 **Learning to Summarize from Human Feedback** 的核心方法：从预训练语言模型出发，先学习人类摘要，再学习人类偏好，最后用 PPO 优化摘要策略。

- 论文原文：[2009.01325v3.pdf](../2009.01325v3.pdf)。
- 阅读笔记：[论文总结.pdf](../论文总结.pdf)。
- 第一版基座：`Qwen/Qwen2.5-0.5B`，使用 Base 版本。
- 硬件：单张 RTX 3090，按标准 24GB 显存规格规划。
- 任务：英文 Reddit TL;DR 摘要。
- 最终比较：**Base、SFT、SFT+PPO**。
- RM 是评分器，不是第四个参与摘要生成的模型。

第一版优先验证完整方法和实验可信度，不以重现原文的偏好率为承诺。原文使用 GPT-3 风格的 1.3B/6.7B 模型；本实验更换模型、分词器、数据规模，并在 PPO 策略更新中使用 LoRA，属于资源受限的方法复现。原文的 CNN/DailyMail 迁移实验、多轮新增人工标注、大规模消融暂不列入第一版。

**完成条件分两层：**

1. 工程完成：三个训练阶段正确执行，模型能保存和重载，能够重复生成评测结果。
2. 研究结果：独立评测说明 PPO 相对 SFT 是改善、无明显差异还是退化。没有显著提升也必须如实报告，不能用训练奖励替代真实质量证据。

## 2. 为什么训练不需要购买 API

本方案下载 Qwen 权重，在 3090 上前向计算、反向传播和更新参数。普通商业推理 API 是把输入发给远端模型获取输出，并不能直接提供本次本地 PPO 所需的模型参数和梯度。

| 阶段 | 训练信号来自哪里 | 是否需要付费模型 API |
| --- | --- | --- |
| SFT | 公开数据中的人类参考摘要 | 不需要 |
| RM | 公开数据中人类对两份摘要的偏好标签 | 不需要 |
| PPO | 本地训练的 RM 分数与 KL 惩罚 | 不需要 |
| 最终评测 | Qwen API 裁判 + 本地补充指标 | 按用户决定使用付费 API；人工抽查仅用于质量校验 |

原作者已公开偏好数据，第一版直接复用，不重新调用大模型生成偏好。模型下载和数据下载需要网络，但不等于购买模型调用额度。**训练阶段 API 预算仍为 0；最终评测改用 LLM-as-a-judge，费用单列于第 6.6 节。** 本地训练另有电费、磁盘占用和人工时间成本。

2026-09-20 用户确定采用 LLM-as-a-judge，正式评测实际使用北京地域固定版本 `qwen3-max-2026-01-23`。API 连通性、结构化输出和正式调用均已验证；结果统一标为“Qwen 裁判偏好”，不等同于原论文的人类偏好结果。密钥值没有写入代码、日志或本文。

## 3. 模型流向与训练产物

```text
Qwen2.5-0.5B Base
        │ 帖子 + 人类参考摘要
        ▼
       SFT ───────────────────────────────┐
        │                                │
        │ 复制骨干，加标量评分头            │ 复制生成模型
        ▼                                ▼
       RM                           Actor / Reference
        │ 人类比较数据训练                 │
        ▼                                │
    训练好的 RM ──评分─────────────────── PPO
        │                                │
        └─独立复制为 Critic 初始化         ▼
                                    最终摘要策略
```

| 对象 | 初始化 | 训练方式 | 保存产物 |
| --- | --- | --- | --- |
| SFT | Qwen Base | 优先全参数微调 | 完整 SFT 权重与 tokenizer |
| RM | SFT 骨干 + 新评分头 | 优先全参数微调 | 骨干、评分头、奖励中心化常数 |
| Actor | SFT | PPO 期间只训练 LoRA | LoRA 权重、所依赖的 SFT checkpoint 标识 |
| Reference | SFT 独立副本 | 始终冻结 | 记录 SFT 路径与内容校验标识 |
| Critic | 训练好的 RM 独立副本 | PPO 期间优先全参数更新 | 价值网络完整状态 |

Actor 和 Critic 不共享可训练参数；RM 和 Critic 也不是同一个 Python 对象。PPO 更新 Critic 时，RM 必须保持不变。

先使用显式 Reference，便于核验。若之后为省显存改为“关闭 PPO adapter 得到参考策略”，必须确认关闭后对应的是完整 SFT 模型，而不是原始 Base。

## 4. 硬件与软件配置

### 4.1 硬件和资源预算

| 项目 | 第一版建议 |
| --- | --- |
| GPU | 1 × RTX 3090 24GB，训练时尽量独占 |
| 系统内存 | 建议 32GB；64GB 更利于缓存和必要的 CPU 卸载 |
| 空闲磁盘 | 建议预留 80～120GB SSD；实际由 checkpoint 数量决定 |
| 训练系统 | 优先 Linux；Windows 可使用具备 CUDA 支持的 WSL2 环境 |
| 文档工作区 | 当前论文目录可用于编辑；训练必须运行在实际连接 3090 的机器上 |
| 显存目标 | 长序列压力测试后，峰值尽量控制在约 21GiB 以下，留出运行余量 |

Qwen2.5-0.5B 官方模型卡给出的参数量约为 0.49B，单份 BF16 权重约 0.98GB。训练还需要梯度、优化器状态、激活、生成缓存及 logits，因此不能用权重大小代表训练显存。[模型来源](https://huggingface.co/Qwen/Qwen2.5-0.5B)

预算级估计：SFT/RM 各自按约 8～16GiB、PPO 按约 12～22GiB 安排余量。这些不是测量结果，也不是保证能放下的上限。尤其需要覆盖最长输入、最长输出和首次优化器更新后的显存峰值。

### 4.2 软件选型与版本记录

| 组件 | 方案 |
| --- | --- |
| Python | 3.11，独立虚拟环境 |
| PyTorch | 选择与 GPU 驱动匹配的 CUDA 构建，安装后锁定精确版本 |
| Transformers | 使用兼容 Qwen2 和所选 TRL 的版本 |
| TRL | 第一候选为 `0.24.0`，仅作为待验证起点，不宣称兼容性已实测 |
| PEFT | 用于 PPO Actor 的 LoRA，安装后锁定版本 |
| Accelerate | 单卡训练组织和混合精度 |
| Datasets | 数据加载、清洗和固定样本划分 |
| 指标与记录 | ROUGE、JSONL/CSV、本地 TensorBoard |
| 注意力 | 优先 PyTorch SDPA；第一版不强制编译 FlashAttention |

选用 TRL 0.24.0 时，其项目声明要求 `transformers>=4.56.1`、`accelerate>=1.4.0`、`datasets>=3.0.0`。这些是依赖下限，不代表任意更高版本都已兼容；先验证一组具体版本，再写入锁定文件。[依赖声明](https://github.com/huggingface/trl/blob/v0.24.0/pyproject.toml)

TRL 的 PPO 接口可能迁移，不混用最新版示例和旧版库。实现基于对应版本的 [PPO 文档](https://huggingface.co/docs/trl/v0.24.0/en/ppo_trainer)，必要修改保留补丁与理由。

初始不引入多 GPU、vLLM、DeepSpeed 或 4bit 量化。只有实测暴露瓶颈时，才增加相应优化，避免把环境复杂性误当成算法问题。

### 4.3 全局约定

- 初次试验随机种子 `42`；配置确定后可扩展到 `43`、`44`。
- 三组摘要模型使用同一个 tokenizer、提示格式及最终评测规则。
- BF16；AdamW 的优化器状态精度由实现确认并记录，不能假设全部状态都是 BF16。
- 梯度检查点用于训练；生成时切换至正确的缓存模式，验证切换后输出和训练正常。
- 初始化时核对 PAD、EOS 和 attention mask；不直接照抄其他模型的 token ID。
- 保存模型、数据的 revision/commit、抽样 ID、完整配置、依赖版本和运行命令。

## 5. 数据准备与实验规模

### 5.1 三种数据各自的作用

| 数据 | 推荐来源 | 处理后的结构 |
| --- | --- | --- |
| SFT | [trl-lib/tldr](https://huggingface.co/datasets/trl-lib/tldr) | `post_id, prompt, completion` |
| RM | [openai/summarize_from_feedback](https://huggingface.co/datasets/openai/summarize_from_feedback) 的 `comparisons` | `post_id, prompt, chosen, rejected` |
| PPO | 已划入训练区的 TL;DR 帖子 | `post_id, prompt`，训练接口不传参考摘要 |

按 `choice` 确定偏好方向，不能假设数组中第一个摘要就是 chosen。原始数据里的标注员备注、候选来源模型名和偏好标签不拼进模型输入，避免泄漏答案。

公开偏好候选来自原论文模型，不是 Qwen。第一版复用现成标签是明确的复现改动。RM 验证除了原数据偏好准确率，还要检查它对新生成 Qwen 摘要的评分是否合理。

### 5.2 数据划分原则

1. 优先尊重公开数据的训练/验证/测试边界，保存原始 split 字段。
2. 以帖子 ID 和规范化内容哈希识别重复；同帖多条比较属于同一组。
3. 先保留最终测试帖子，再从训练部分提取开发验证集；最终测试绝不用于选 checkpoint 或调超参数。
4. 所有训练集合排除验证/测试帖子。SFT、RM、PPO 的训练帖子之间可以重叠，这是允许的，不要误判为泄漏。
5. RM 验证集若缺少独立 test，则从训练帖子按组留出开发部分，官方验证部分保留为最终 RM 检查；不得按单条比较随机切分同帖样本。
6. 记录每次筛选前后的数量、长度分位数及丢弃原因。表中数量是清洗后的目标；不足时使用实际数量，不从验证/测试补训练数据。

### 5.3 分阶段数据量

| 阶段 | 小样本调试 | 首轮实验 | 后续扩大，仅在前一轮有效时 |
| --- | --- | --- | --- |
| SFT | 512 条、少量更新 | 20,000 条、1 epoch | 50,000 条或更多清洗后的训练数据 |
| RM | 512 对、少量更新 | 10,000 对、1 epoch | 20,000 对或更多有效训练比较 |
| PPO | 256 条生成轨迹 | 10,240 条生成轨迹 | 20,480～51,200 条轨迹 |
| 生成任务开发集 | 32 篇 | 固定 200 篇 | 保持固定 |
| 最终生成任务测试集 | 不用于调试 | 固定 500 篇 | 可另预留更多测试帖子 |
| RM 开发/最终检查 | 各自独立 | 各目标 1,000 对，按帖子隔离 | 视有效数据量扩大 |

轨迹指一次“帖子→当前策略生成摘要”。10,240 条轨迹不必来自 10,240 个不同帖子；如果重复采样，记录独立帖子数和采样次数。不能把 PPO 轨迹数、外层 rollout 轮数和 optimizer step 混为一谈。

### 5.4 统一提示与长度

```text
SUBREDDIT: r/...
TITLE: ...
POST: ...
TL;DR:
```

- 使用 completion 格式，不依赖 Instruct 模型的聊天模板。
- 调试阶段：prompt 上限 512、completion 上限 64 tokens。
- 首轮正式配置：prompt 上限 768、completion 上限 128，总长度上限 896 tokens。
- 正式阶段将上限从调试的 64 提高到 128，是为了减少参考摘要被截断；需重新进行峰值显存与速度测试。
- 长度均按 Qwen tokenizer 统计。原文其他分词器的 token 数不可直接当成相同长度。
- 第一版优先过滤超长训练样本，保留完整文章和摘要，不把截掉关键事实的文章与完整摘要强行配对。RM 一对中任一候选超限时，整对处理，不能只截差的一侧。
- 验证/测试使用预先确定的同样长度范围，并报告这是短文本子集的结果；不宣称覆盖完整 TL;DR 长度分布。
- EOS 纳入目标长度预算。PAD 与 EOS 如复用同一 ID，必须通过 attention mask 区分，不能把真实结束 token 的损失也全部屏蔽。

### 5.5 本地下载与存储规划（只规划，未下载）

2026-09-20 仅查询了 Hugging Face 文件列表、网页和仓库元数据，没有下载 Parquet/JSONL 数据内容，也没有调用 `load_dataset` 建立数据缓存。

**结论：第一版所需的文本数据可以完整保存在本地，下载量约 167 MB，无须因容量改用在线流式训练。** 这里的 MB 按十进制计算，不包含模型权重、运行缓存和 checkpoint。

| 用途与格式 | 文件 | 文件清单中的大小 |
| --- | --- | --- |
| SFT：TRL 整理版 TL;DR Parquet | train | 110,378,163 字节，约 110.4 MB |
| 同上 | validation | 6,111,474 字节，约 6.1 MB |
| 同上 | test | 6,213,361 字节，约 6.2 MB |
| RM：OpenAI 数据的 HF 自动转换 Parquet | comparisons/train | 21,115,502 字节，约 21.1 MB |
| 同上 | comparisons/validation | 22,831,890 字节，约 22.8 MB |
| **五个数据文件合计** | | **166,650,390 字节，约 166.7 MB** |

大小来源为 [TL;DR 文件目录](https://huggingface.co/datasets/trl-lib/tldr/tree/main/data) 和 [OpenAI comparisons 转换分支](https://huggingface.co/datasets/openai/summarize_from_feedback/tree/refs%2Fconvert%2Fparquet/comparisons) 的文件元数据；下载时需再次核对 revision 和文件大小。这里选用的是便于读取的 Parquet 版本，不能把它们与原作者 Azure 上的原始 JSON 文件大小混为一谈。

OpenAI 数据仓库 main 分支目前约 13.3 kB，只有说明与旧式加载脚本，实际数据不在这些小文件里。后续优先读取转换分支中的 Parquet，避免依赖旧式 dataset script；转换版本需要固定 commit，并核对原始 `split`、`batch`、`choice` 等字段是否保留。不要只根据 HF 外层 `validation` 名称就丢弃原有 valid1/valid2 的区别。若转换文件缺字段或不可用，再规划从原作者链接读取原始 JSON，并重新核实大小。

**计划执行顺序：**

1. 固定两个数据仓库的 commit，建立包含来源、文件名、字节数、revision、预期划分的清单。
2. 将上表五个文件下载到训练机器的本地 SSD；先完整保留来源文件，再做筛选抽样。全量下载不等于全量训练。
3. TL;DR 用于 SFT 和 PPO，PPO 只取训练帖子，因此不额外下载第三套 PPO 数据。
4. 第一版不下载 `axis` 评分数据或单独的 CNN/DailyMail 数据；comparisons 中若含非 TL;DR 记录，在本地清洗时排除。
5. 保留原始 Parquet，在处理区生成 SFT/RM 子集和 PPO prompt；抽样仍按第 5.2 节先隔离测试再进行。
6. 把模型、数据和依赖都准备好后验证离线加载，再开始正式训练，避免训练期间反复联网。

建议将数据文件区分为以下计划目录，当前尚未创建：

```text
data/
├── raw/tldr/                  # 下载的三个 TL;DR Parquet
├── raw/comparisons/           # 下载的两个偏好 Parquet
├── processed/                # 清洗、tokenize、抽样后的本地数据
├── splits/                   # 帖子 ID/哈希及划分清单
└── manifest.json             # 来源、版本、字节数、下载后校验和
```

**数据区预留 5GB 即可作为首轮保守规划**：约 0.17GB 来源文件，其余用于解码后的 Arrow、tokenization、清洗副本和缓存。5GB 是空间预算，不是实测占用；避免每次调参都保存一份完全相同的数据。此前建议的 80～120GB 是包含模型、优化器状态、多个训练 checkpoint 和日志的整个项目预算，并不是数据集下载量。

只按传输量估算，167 MB 在持续 1 MB/s 时约 3 分钟，在 5 MB/s 时约半分钟；实际还受连接、校验、限速和重试影响。这是网络传输估算，不是本机测速。

## 6. 各阶段操作与配置

以下参数是起步值，不是原论文超参数的逐项复刻，也不是已搜索出的最优组合。每次修改记录原因；先用开发集判断，再固定配置做最终测试。

### 6.1 阶段 0：环境检查、数据审计和基线

**做什么：**

1. 在实际 3090 机器上确认驱动、CUDA、BF16、显存和磁盘。
2. 下载模型与数据，记录版本；完成第 5 节的数据清洗与划分。
3. 加载 Base，对固定开发样本生成摘要，保存原始输出。
4. 分别验证语言模型、标量评分模型和 LoRA Actor 的前向与反向。
5. 用最长配置做包含优化器更新的试运行；只测模型加载或推理不算训练显存检查。

**产物：**环境清单、数据审计记录、划分清单、Base 开发样例、初步显存记录。

**通过标准：**样本方向正确；无训练/测试帖子重叠；模型能保存和重载；损失与梯度有限且非异常值。

### 6.2 阶段 1：SFT，学习生成摘要

只对 completion 和有效 EOS 计算交叉熵；prompt 与 padding 的 label 设为忽略值。第一版关闭跨样本 packing，降低边界处理出错的机会。

| 参数 | 首轮值 |
| --- | --- |
| 初始化 | Qwen2.5-0.5B Base |
| 更新范围 | 全参数 |
| 训练条数 / epoch | 20,000 / 1 |
| micro-batch | 每卡 1 条 |
| 梯度累积 | 16 |
| 有效 batch | 16 条 |
| 初始学习率 | `1e-5` |
| 优化器 | AdamW，betas `(0.9, 0.999)`，epsilon `1e-8` |
| weight decay | `0.01` |
| 调度 | 3% warmup，随后线性下降 |
| 最大梯度范数 | `1.0` |
| 精度 / 检查点 | BF16 / 开启梯度检查点 |
| 验证与保存 | 每约 250 个 optimizer steps 及结束时 |

若实际恰有 20,000 条且训练 1 epoch，有效 batch 为 16，则约 1,250 次 optimizer 更新。样本过滤和最后一个 batch 的处理会影响精确步数。

**验收：**验证损失和开发集摘要一起检查；相对 Base，输出更稳定地执行摘要任务，能结束，严重重复或无关续写减少。用开发集选择 checkpoint，不以训练损失最低作为唯一依据。

**产物：**SFT checkpoint、tokenizer、训练日志、开发集样例、训练时长和显存峰值。

### 6.3 阶段 2：RM，学习人类偏好

从选定 SFT 的骨干初始化标量评分模型，明确保存新建评分头；不是重新从 Base 开始，也不是要求模型输出文字评分。

对同一帖子的人类偏好摘要与非偏好摘要分别计算分数，采用：

```text
RM loss = -log sigmoid(score_chosen - score_rejected)
```

模型在约定的序列结束位置取分数。训练、验证、PPO 评分必须使用一致的拼接、EOS 和取分位置规则。

| 参数 | 首轮值 |
| --- | --- |
| 初始化 | SFT 骨干 + 随机初始化标量评分头 |
| 更新范围 | 骨干和评分头全参数 |
| 训练规模 | 10,000 对，先做 1 epoch |
| micro-batch | 1 对，即 2 条候选序列 |
| 梯度累积 / 有效 batch | 16 / 16 对 |
| 初始学习率 | `5e-6` |
| 优化器 | AdamW，betas `(0.9, 0.999)`，epsilon `1e-8` |
| weight decay / 梯度裁剪 | `0.01` / `1.0` |
| 调度 | 3% warmup，随后线性下降 |
| 验证与保存 | 每约 125 个 optimizer steps 及结束时 |

名义上约 625 次 optimizer 更新。只有验证尚未恶化时才考虑第二个 epoch；小偏好集容易过拟合。

**奖励标定：**训练完成后，用固定的训练区参考摘要计算平均分，将其减去，使这批参考摘要的均分为 0。中心化常数固定保存，PPO 期间不逐批重估。首轮不额外缩放标准差；同时记录分数分布，作为 KL 系数选择的依据。

**验收：**在独立帖子上计算偏好准确率和按帖子 bootstrap 的区间。明显高于 50% 才说明学到了有用信号；“高于 50%”还不代表足以进行强 PPO 优化。开发阶段可把 60% 左右设为值得继续尝试的工作目标，但它不是保证、原文复现门槛或强制刷到的数字。

额外人工检查约 50 组 Qwen SFT 候选，包含事实错误、信息遗漏和长度差异，确认 RM 不只是奖励长文本。若准确率接近随机或有明显取巧模式，优先检查数据方向、取分位置、评分头和过拟合。

**产物：**完整 RM、中心化常数、偏好准确率与区间、长度偏好诊断、Qwen 样本检查记录。

### 6.4 阶段 3：PPO，优化摘要策略

**初始化：**Actor 与 Reference 来自同一个 SFT checkpoint；Actor 添加新 LoRA，Reference 冻结；RM 固定为阶段 2 的模型；Critic 独立复制 RM 并允许更新。

如果奖励中心化使用外置常数，Critic 初始化时也要核对预测值尺度，不要只复制骨干而漏掉评分头和标定约定。Critic 的逐 token 价值预测仍需通过 PPO 学习，RM 初始化不等于价值估计已经正确。

每个外层训练循环：

1. 取训练帖子，用当前 Actor 采样摘要，保存采样时的 log-probabilities。
2. 用冻结 Reference 计算参考 log-probabilities，用冻结 RM 计算摘要奖励。
3. 在有效生成 token 上加入 KL 惩罚，终局加入摘要奖励。
4. 用 Critic 估计价值，计算优势和回报。
5. 对当前这批轨迹做有限轮 PPO 裁剪策略更新与价值更新。
6. 丢弃过旧轨迹，重新采样；不把同一批旧轨迹无限训练。

概念上，总奖励为 `RM 分数 - beta × 相对 SFT 的采样 KL`。采样 log-ratio 可在有限样本中为负，不应误认为每条轨迹都必须产生非负值。还要区分“相对 SFT 的 KL”和“新旧 PPO 策略之间的近似 KL”。

| 参数 | 首轮值 / 约定 |
| --- | --- |
| Actor 更新 | LoRA，rank `16`、alpha `32`、dropout `0` |
| LoRA 层 | `q_proj, k_proj, v_proj, o_proj, gate_proj, up_proj, down_proj` |
| Critic 更新 | 独立 0.5B 网络，全参数 |
| Reference / RM | 冻结、推理模式，不保存反向图 |
| 总轨迹数 | `10,240` |
| 每轮 rollout | `32` 条 |
| 训练 micro-batch | `1` 条 |
| 梯度累积 | `32` |
| `num_mini_batches` | `1`，先避免复杂的批次划分 |
| 每批 PPO epochs | `2` |
| 生成、参考评分、RM 评分分块 | 从每块 `1` 条开始，实测后增加 |
| Actor / Critic 学习率 | 第一版统一 `3e-6`，稳定后再考虑分组学习率 |
| 优化器 | AdamW，betas `(0.9, 0.999)`，epsilon `1e-8` |
| 调度 / weight decay | 固定学习率 / `0` |
| `cliprange` / `cliprange_value` | `0.2` / `0.2` |
| `vf_coef` | `0.1` |
| `gamma` / GAE `lambda` | `1.0` / `0.95` |
| KL 系数 `beta` | 从 `0.05` 开始，按实际 RM 尺度和开发表现调整 |
| KL estimator | `k1`，明确记录定义 |
| 奖励 whitening | 首轮关闭；优势归一化遵循所固定实现并记录 |
| rollout 温度 | `0.7`，不用额外 top-k/top-p 截断 |
| 最大生成长度 | `128`，从 EOS 后屏蔽奖励、损失和统计 |
| 未输出 EOS 惩罚 | 首轮关闭；若严重不结束，先修 EOS/SFT，再单独加入并记录此改动 |
| 最大梯度范数 | `1.0` |
| 开发评测 / checkpoint | 每 `32` 个外层 rollout 循环及结束时 |

在所选 TRL 0.24.0 代码中，单卡 rollout batch 由训练 micro-batch 与累积步数相乘得到；因此本表的 `1 × 32 = 32`，总共 `10,240 / 32 = 320` 个外层循环。`num_ppo_epochs=2` 指同一批轨迹的更新轮数，不是把帖子数据集训练两遍。正式运行前打印实际派生 batch 参数并核对。[PPO 实现](https://github.com/huggingface/trl/blob/v0.24.0/trl/trainer/ppo_trainer.py)

**实现检查点：**

- rollout 温度与更新时计算 log-probability 的约定一致，正确保存旧策略概率。
- LoRA 初始输出与 SFT 基本一致；一次更新后 Actor/Critic 改变，Reference/RM 不变。
- reward 只落在正确终止位置；padding、EOS 后 token 不参与有效损失。
- RM 输入包含正确原文；没有把参考摘要或人类偏好标签泄漏给 Actor。
- 生成时显存分块不等于训练 micro-batch，需分别配置；同时检查返回 logits/缓存的累计占用。
- Actor 的 LoRA 梯度确实存在，不能出现“脚本运行但参数未更新”。

**监控：**原始与中心化 RM 分数、KL 惩罚后回报、相对 Reference 的 KL、新旧策略近似 KL、裁剪比例、价值损失、梯度范数、实际生成长度、EOS 比例、重复与空输出、显存峰值、轨迹吞吐。

**停止/回退信号：**出现 NaN/Inf；KL 或裁剪比例持续异常；摘要退化为重复或空白；开发样例质量下降而 RM 分数持续提高。先回退 checkpoint，检查奖励尺度与 mask，再一次只调整一项，例如降低学习率/更新轮数或提高 KL 约束。不能机械追求 RM 分数越高越好。

**产物：**Actor adapter、SFT 依赖标识、Critic、训练状态、开发曲线、样例和显存/吞吐记录。不能只保存 Actor 就声称可以恢复 PPO；恢复还需要 optimizer、scheduler、随机数和训练进度，并验证所选 Trainer 是否确实保存这些状态。

### 6.5 阶段 4：最终评测

配置和 checkpoint 在开发集上选定后，再对保留测试集运行一次主评测。

| 项目 | 规则 |
| --- | --- |
| 比较组 | Base、SFT、SFT+PPO；均为同一 0.5B 基座 |
| 测试帖子 | 固定 500 篇，保存 ID |
| 推理方式 | 三组一致使用贪心解码，最多 128 新 tokens，相同 EOS 与 prompt |
| 主要对比 | PPO 对 SFT；另比较 SFT 对 Base、PPO 对 Base，共 3 组 |
| 主评测 | LLM-as-a-judge；建议固定 `qwen3-max-2026-01-23` |
| 调用方式 | 每篇每组 A/B、B/A 各一次；500 × 3 × 2 = 3,000 次调用 |
| 人工抽查 | 可选抽查 30～50 篇，检查明显误判，不作为 500 篇主评测替代 |
| 显示方式 | 隐去模型名，原文与两份摘要同时展示；每次独立请求 |
| 返回项 | 总体偏好 A/B/tie、事实错误、重要遗漏与简短依据 |
| 自动指标 | ROUGE-1/2/L、词数/token 数、重复率、空输出率、EOS 比例 |
| 统计 | 按帖子 bootstrap 95% 置信区间，记录随机种子 |

每次判断先映射回真实模型，再将目标模型的胜/平/负记为 1/0.5/0。每篇每组的最终分数取两个顺序得分的平均，最后对帖子平均。单独报告原始胜/平/负、顺序一致率和冲突率；不得丢弃冲突样本以抬高胜率，也不能把冲突都冒称为裁判明确给出的平局。按帖子 bootstrap，不能将 3,000 次相关调用当成 3,000 篇独立测试样本。

长度是关键混杂因素：报告各组长度分布，并做长度相近样本的敏感性分析；相同的最大生成长度不代表实际长度一致。不能仅凭 PPO 更长、ROUGE 更高或训练 RM 更满意就宣称“人类更喜欢”。

优先评判忠实于原文和覆盖要点，不奖励凭空补充信息。固定英文评判提示，要求原文和候选摘要只是待评数据，不执行其中的指令；不联网检索，不把某个 checkpoint 的训练奖励透露给裁判，不提供模型名称或“PPO 应更好”的暗示。

先在独立开发样本上校准裁判和提示，必要时与少量人工判断对照；在最终测试前冻结。候选裁判能力是待验证的工程选择，不能仅按价格或 Max/Plus 名称推断它在摘要评判上的准确率。LLM 裁判存在位置、冗长和自偏好等风险；本实验的裁判与被评模型同属 Qwen，也不能预设家族风格偏好会自动抵消。[方法参考](https://arxiv.org/abs/2306.05685)

## 7. 预期时间、估算依据与校准

### 7.1 首轮预算

下表是 **0.5B、20k SFT、10k RM、10,240 PPO 轨迹、单个 seed** 的工程预算。不是 3090 实测，不包含大规模调参或全部扩大数据实验。默认本机训练、没有 CPU 卸载，实际 token 长度、PPO 生成实现、磁盘和散热都会改变耗时。

| 工作 | 暂定时间预算 | 说明 |
| --- | --- | --- |
| 环境与数据准备 | 人工约 2～6 小时 | 下载耗时另受网络影响；首次环境排错可能更久 |
| 小样本检查与性能基准 | GPU 约 0.5～2 小时 | 覆盖 SFT、RM、PPO 和最长序列 |
| SFT 正式首轮 | GPU 约 1～4 小时 | 20k 条、1 epoch |
| RM 正式首轮 | GPU 约 1～4 小时 | 10k 对、1 epoch；每对两条序列 |
| PPO 正式首轮 | GPU 约 4～16 小时 | 10,240 条轨迹、每批 2 轮更新，通常最慢 |
| 500 篇 × 3 模型生成和指标 | GPU 约 0.5～2 小时 | 不含人工阅读与标注 |
| Qwen 裁判 3,000 次调用 | API 墙钟暂预留 1～3 小时 | 非本地 GPU 时间；若可持续 60 请求/分钟，仅吞吐下限约 50 分钟，实际受并发、延迟和限额影响 |
| 可选人工抽查 30～50 篇 | 人工约 1～2 小时 | 校验裁判明显错误；不作为主评测 |

一次首轮完整 GPU 流程，含小样本检查，暂按 **7～28 小时** 预算。为重跑和检查留余量，可预留 **10～40 GPU 小时**。这不是保证按时完成；首次代码实现和环境调试另外预留约 **2～5 个工作日**，边学边实现可能需要 **1～2 周或更久**。

若做三个 seed，重复的正式训练与评测成本近似乘三，环境准备不必重复。若仅重跑 PPO 而复用同一 SFT/RM，报告应说明它只测量 PPO 阶段随机性，不能称为完整流程的三次独立复现。

### 7.2 时间区间是怎样得到的

这些速率仅用于解释预算，不是宣称硬件已达到该性能：

- SFT：假设清洗后平均总长度约 400 tokens，则 20k 条约 800 万有效 tokens。若完整训练过程平均处理 600～2,500 有效 tokens/s，约 0.9～3.7 小时，按 1～4 小时预算。
- RM：假设每候选总长度约 400 tokens，10k 对同样约 800 万有效 tokens；实际还受两候选如何打包影响，因此仍需独立测速，暂按 1～4 小时。
- PPO：若包含采样、Reference/RM/Critic 前向及 PPO 更新的完整吞吐为 0.18～0.70 条轨迹/s，10,240 条约 4.1～15.8 小时。
- 测试生成：1,500 份摘要若吞吐为 0.2～0.8 份/s，约 0.5～2.1 小时。

动态 padding 会让实际计算 token 数多于有效 token 数；不少生成实现即使早遇到 EOS，仍可能按固定生成长度执行部分计算。因此不能只用平均可见摘要长度推断 PPO 速度。

### 7.3 真正启动前的测速流程

1. 完成预热，确保优化器状态已经建立。
2. SFT/RM 分别测至少 20 个完整 optimizer steps，包含全部梯度累积；记录中位数和较慢分位数。
3. PPO 测至少 10 个完整外层循环，计时包含生成、全部打分、优势计算和两轮更新。
4. 用正式最长长度额外做压力测试，记录峰值 allocated/reserved 显存。
5. 独立计量保存 checkpoint 和开发评测的时间。
6. 在本报告补上实测表，用实测替换暂定区间后再开长任务。

```text
SFT 时间 ≈ ceil(有效训练条数 × epoch / 有效 batch) × 每 optimizer step 秒数
RM 时间  ≈ ceil(有效训练对数 × epoch / 有效 pair batch) × 每 optimizer step 秒数
PPO 时间 ≈ ceil(总轨迹数 / 每轮轨迹数) × 每完整 rollout 循环秒数
总时间   = 训练 + 开发评测 + 保存 + 最终生成评测
```

| 实测项目 | SFT | RM | PPO |
| --- | --- | --- | --- |
| GPU / 驱动 / 关键依赖 | RTX 3090 24GB / 565.57.01 / PyTorch 2.6.0+cu124、Transformers 4.56.2、TRL 0.24.0 | 同左 | 同左 |
| 实际样本量 | 20,000 条，1 epoch | 10,000 对，1 epoch | 10,240 条轨迹，320 个 rollout batch |
| 每 step / 完整 rollout 耗时 | 约 2.13 秒/optimizer step | 约 2.50 秒/optimizer step | 平均约 81.05 秒/rollout batch |
| 峰值显存 allocated / reserved | 4.72 / 7.20 GiB | 4.70 / 4.93 GiB | 10.30 / 10.61 GiB |
| 正式运行实际时长 | 44 分 23 秒 | 26 分 30 秒 | 7 小时 12 分 15 秒 |

## 8. 预期效果与结论边界

| 阶段 | 合理期待 | 不应提前承诺的结果 |
| --- | --- | --- |
| Base | 能产生部分摘要，但格式、完整性和任务稳定性可能不足 | Base 一定表现很差；预训练可能已见过类似数据 |
| SFT | 更稳定地产生短摘要，减少无关续写 | 对所有指标都提升或达到原论文监督模型水平 |
| RM | 在未见帖子上学到一定人类偏好信号 | 与人类完全一致、对 Qwen 新输出可靠无误 |
| PPO | 在适度优化下可能提高相对 SFT 的偏好 | 必然优于 SFT、必然超过人类参考摘要 |

工作假设是 `SFT 优于 Base，适度 PPO 有机会优于 SFT`；后半句尤其需要实验验证。小模型能力、RM 误差、公开偏好与当前输出的差异、LoRA 可更新空间、KL 系数都可能使 PPO 无提升或退化。

可以把“PPO 对 SFT 的盲评偏好分数超过 50%”作为观察方向，但科学结论要看区间：若 95% 区间包含 50%，应写“未获得明确改善证据”。作为量级参考，无平局且独立二项判断时，50% 附近的 95% 误差范围在 100 篇约为 ±10 个百分点、500 篇约为 ±4.4 个百分点；有平局或相关标注时按实际 bootstrap 处理。

不得把原论文的胜率搬作本项目目标分数。本项目结论只适用于所选 Qwen 模型、清洗后的长度范围、训练预算和评测方式。

## 9. 显存不足和效果不佳时的处理顺序

| 情况 | 优先操作 |
| --- | --- |
| PPO 生成 OOM | 减小生成与打分分块，检查是否累计保存全部 logits/KV 缓存 |
| 反向传播 OOM | 确认梯度检查点生效，micro-batch 降至 1；不只减 rollout 数 |
| 仍然 OOM | 调小长度并重新审计数据与评测范围，或者 Critic 改 LoRA；逐项记录改动 |
| SFT/RM OOM | 确认各阶段独立进程运行；必要时改 LoRA，但重新定义本次实验配置 |
| 最后仍不够 | 再考虑量化冻结模型或 CPU 卸载，同时重新估计耗时 |
| RM 接近随机 | 检查 choice 方向、数据拼接、取分位置、评分头与训练验证隔离 |
| PPO 奖励涨但质量跌 | 停止继续推高奖励，回看开发样例、长度与 KL，降低更新强度 |
| 训练太慢 | 按生成、打分、更新分段测速，再决定增大分块或缩短长度 |

不要同时更换模型、数据、长度和学习率，否则无法判断是哪项因素带来变化。

1.5B 只作为后续扩展。尤其独立 Critic 的全参数训练显著增加显存，不能把 0.5B 配置只替换模型名就宣称 3090 可运行；需重新设计 Critic 更新方式并做显存测试。两种模型大小的算法比较应各自在相同基座内完成。

| split | pairs / posts | 偏好准确率 | 95% CI | 平均 margin | reward 与候选长度差相关系数 |

### 12.5 结论与限制

本轮实现了数据准备、SFT、RM、PPO、三模型生成、自动指标和独立盲评的完整闭环。结果支持以下有限结论：在本实验的单 seed、0.5B Qwen、固定短文本子集和 Qwen 裁判下，SFT 明显优于 Base；PPO 相对 SFT 获得了显著高于 0.5 的 Qwen 裁判偏好分数，但没有同步提高 ROUGE-L。

不能把 `0.7188` 写成论文的人类偏好复现值，原因包括：

- 只运行一个 seed，尚未测量训练随机性；
- 模型、分词器、样本规模、Actor LoRA 和 PPO 预算均不同于原论文；
- 主评测是单一 Qwen 裁判而非独立人工标注，且换位一致率并非 100%；
- RM 有明显长度偏差，PPO 输出也比 SFT 长，因此更高裁判偏好可能部分包含长度/覆盖度效应；
- 14/3,000 个唯一判断因内容过滤缺失，各配对最终覆盖 497～498 个完整帖子；
- 生成评测是清洗后的长度受限 TL;DR 子集，不代表完整分布或 CNN/DailyMail 迁移表现。

综合判断：**工程复现成功，方法方向得到支持，但这不是原论文规模和人工评测条件下的数值复刻。** 下一步若要把结论升级为更强的研究证据，优先补做 2 个独立 seed、对 50～100 篇测试帖人工盲评，并对摘要长度做匹配或消融，验证 PPO 优势是否仍然存在。
